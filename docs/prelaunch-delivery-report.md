# 上线前缺陷修复与隔离复测交付报告（2026-09-29）

## 结论与范围

本轮按照《项目上线前测试反馈报告》QA-01—QA-13 的既定优先级，完成 P0 部署安全/核心报修、P1 页面契约/任务运行时、P2 回归脚本/能力边界三组修复。不修改业务需求、不删除遗留路由、不修改 `drizzle` 迁移表结构；旧 Supabase CRUD 在服务端鉴权后返回 503，新业务以 PostgreSQL 为准。最终复查另补上身份仓储、AI 任务仓储、Skill Port 三处生产后端选择：PG 优先、无 PG 失败关闭，即使旧 Supabase 凭据仍存在也不调用旧业务链路。以专用隔离数据库 `qa_20260929_a6a3fe` 和生产构建进行有状态回归，**没有把数据写到项目原始数据库**。当前生产构建实例监听 `http://localhost:5000`，仅用于本地查看，签名密钥为进程内临时生成，不可当作校园生产部署密钥。

**本地结论：阶段 A/B/C 的关键门禁在隔离环境通过，不能宣布真实校园阶段 D 或整体生产环境通过。** 学校真实部署仍需进行稳定密钥、第三方渠道、真实硬件、备份恢复、故障与容量测试；不能用 200 页面或模拟模型应答替代外部结果。原报告发现的 71 GET 中 35 个 5xx 的**旧业务能力没有虚构完成**：未迁移旧接口以受控 503 清楚标注，需要后续正式迁移才可开放。

## 【需要确认】与剩余风险

1. 多个有效后勤组织时，报修受理责任如何按楼栋/校区/设备分配？当前安全失败返回409，避免猜组织越权。
2. 原迁移表没有报修联系电话独立列，当前将用户填写的可选电话拼入 `description`。需业务负责人确认是否允许在工单正文存储该个人信息、访问权限及保留期限；如需独立字段，须另行走**明确批准**的迁移方案，本轮没有改表。
3. 校区/组织/班级/楼栋 assignment 的真实混合权限与所有 11 域统计边界，应以多租户真实代表数据再验收；当前自动负例重点覆盖维修组织 A/B。
4. 设置修改、权限策略编辑、旧详情 CRUD、学生失物发布仍未开放；不能因为它们页面能渲染而宣传业务闭环。
5. 短信/邮件/微信登录和消息、门禁真实硬件、远端联邦、WAL 恢复、多实例 HA 尚无实现或真实环境验收；单机短时只读性能不足以代表校园长期生产稳定性。
